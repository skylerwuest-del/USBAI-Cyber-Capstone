# CapStone USB — Hermes in the terminal

Start from the USB folder:

```bash
bash launch.sh
```

The default path serves a USB-local GGUF model with llama.cpp and connects **Hermes Agent
0.21.5** to it. Hermes has real terminal, process, file-reading, file-writing, patching,
search, and task-planning tools. It can execute commands and edit files itself. Everything
is displayed in the terminal. No webpage, browser UI, cloud account, or API subscription
is needed for the default workflow. A loopback HTTP API carries requests between Hermes
and the model process; that API is not a webpage. CAI and LiteLLM are no longer used.

The target remains **Ubuntu 24.04, x86_64**. CPU inference was verified locally;
GPU selection has automated coverage but requires validation on physical GPU hardware.
LLM Fit detects current RAM instead of assuming a fixed capacity.
Python 3.12, Hermes source, its binary dependencies, model weights and server are on
the USB. Dependencies use regular files rather than a symlink-based virtual environment,
so the exFAT drive is supported. The drive must be mounted with permission to execute
its Python and model-server binaries. Launch with Bash because exFAT does not preserve
normal Unix executable bits.

## First setup and everyday launch

From `Source/`, run **one setup command**:

```bash
bash setup.sh
```

The default setup is online. It prepares the checksum-pinned llama.cpp archive, portable
Python, pinned Hermes source and hash-verified dependency wheels. Installed GGUF weights
are preserved; if models are already present, setup does not download model weights.
With no installed models, it prepares the pinned default model. Python handles downloads,
so Snap curl is not required. Dependencies are installed inside this folder, without sudo
or changing your system Python.

Before downloading the default model, setup also checks `models/` beside the
repository and beside the application folder on the same filesystem. A matching
file is copied into the application's model folder and checked against the pinned
SHA-256 in one pass. The source stays intact, and interrupted network downloads
remain available for resuming. USB copying can still take time; watch progress in
`logs/setup.log`.

If the old Ubuntu-library archive is absent, setup collects the required libraries from
the compatible host OS, verifies the server executes, and caches them with a separate
local provenance/checksum manifest (`state/ubuntu-runtime-libs.local.json`). It does not
pretend those generated bytes match the old archive's hash. This bundle was verified on
Ubuntu 24.04 x86_64 with glibc 2.39; other hosts must still pass actual runtime checks.
The host needs Python 3, Linux x86_64 and standard `ldd`/`sync` utilities.

Setup validates local assets, loads the smallest eligible installed model for a quick
check, initializes the real Hermes SDK, reaches `You>`, and sends `/quit`. It never runs
your tasks or password audits. Detailed setup output appends to `logs/setup.log`; readiness
and session checks also appear in `logs/llm-fit-diagnostics.txt`. Setup only reports success
after this check and records `state/setup-ready.json`. It leaves no test server running.

After setup succeeds, the everyday command is:

```bash
bash launch.sh
```

Choose **1** for automatic selection, **2** for the saved default, or **3** for a
manual choice. Each opens the original application menu; choose **1** there to start chat. Setup is not required on every launch. For a later repair without internet:

```bash
bash setup.sh --offline
```

This uses the cached archives and wheels. Keep `hermes/`, `runtime/`, `models/` and the
runtime cache under `state/` together when moving the application. `setup.py`,
`setup_hermes.py` and `prepare.py` are supporting implementation files; you do not need
to run them individually. `setup.sh` is the installation/repair entry point;
`launch.sh` is the main menu entry. The redundant `startup.sh` shortcut was removed;
use `bash launch.sh --chat` for direct chat. Toolkit management retains its optional preparation path; the
unified setup prepares the GGUF/Hermes chat stack.

### Fit policy and limitations

Inspired by [llmfit's hardware/fit/scoring concepts](https://github.com/AlexsJones/llmfit/blob/main/docs/how-it-works.md),
this is an independent standard-library implementation, with no llmfit installation,
model catalog, or online lookup. It reads local Linux CPU/RAM data, cgroup v2 memory
limits and DRM GPU identifiers. A matching ELF server is probed locally with
`--list-devices` to distinguish device presence from runtime support.

Setup now prepares checksum-pinned x86_64 Vulkan and CUDA 12.8 runtimes on the USB
alongside the CPU runtime (about 794 MB of additional compressed downloads). No
ARM runtime or host driver installation is added. Rerun `bash setup.sh` online
once to populate these archives; subsequent offline repairs reuse them.

At launch, local device probes prefer CUDA, then Vulkan, then CPU. Existing host
drivers must support the selected backend. GPU launches use automatic layer
offload and device-memory fitting with a 1024 MiB margin per GPU. Context remains
explicit. `acceleration` in `config.json` can be `auto` (default), `cpu`, `cuda`, or
`vulkan`; `gpu_reserve_mib` adjusts the margin. CPU threads default to all cores
available to the process; an explicit `threads` setting still takes precedence.
The launch reports its backend and thread count. A successful device probe is
not a guarantee that every model operation is supported; model startup errors
remain visible in `logs/server.log` rather than silently reporting success.

Fit remains conservative: it requires the full CPU memory budget and does not
add VRAM to RAM. This can reject a model that would fit with GPU offload; it does
not claim an unmeasured GPU memory budget. Performance histories distinguish
selected runtime/backend and GPU reserve settings. No swap-backed loading is enabled.

Models, archives, dependencies, logs, application caches, GPU shader caches, and
setup download/extraction files stay under the USB application directory. Application session scratch storage is managed separately as described below.
The existing portable Python stays on USB; no new host venv is required. No host
packages or GPU drivers are installed. Explicit user-directed tool commands can
still edit host files; environment redirection is not a filesystem sandbox.
Performance is reported only when actually observed, as described below.

The scanner deduplicates canonical paths, rejects links outside `models/`, and reuses
existing split-file discovery rules. Split GGUF loading remains available through the
original functionality, but automatic fit classifies it Unknown until complete-shard
memory estimation is supported. Unsupported/missing metadata is also Unknown.

Estimates budget resident file bytes, f16 K/V state at the selected profile context,
`max(1 GiB, 20% of weights)` runtime overhead, an extra 256 MiB allowance and a reserve
of `max(1 GiB, 10% of total RAM)` against **current available RAM**, with cgroup limits.
Dense supported architectures use attention dimensions in GGUF metadata. Hybrid Qwen3.5
has an explicitly documented conservative KV bound and larger state allowance in its
profile. These are estimates, not measured peak memory guarantees. Configured context
must fit native context; fit does not silently reduce it. Startup may still reject a
model or quantization unsupported by the bundled llama.cpp build.

Good Fit leaves at least two reserves; Marginal Fit leaves one; Does Not Fit fails a
hard requirement; Unknown lacks safe evidence. Only Good/Marginal candidates are tried.
Scores combine log-scaled tensor parameter capacity (25 points maximum), context (10 maximum),
memory headroom (15 maximum), estimated GPU offload (20 maximum), remaining CPU cost
(10 maximum, scaled down as GPU coverage increases), and quantization (5 or 3).
GPU coverage is the largest device’s reported free VRAM minus `gpu_reserve_mib`
(default 1024 MiB), divided by total estimated model/context/runtime memory and capped
at 100%. Device budgets are not summed. Unknown VRAM or CPU-only mode gets no GPU
credit. RAM eligibility remains conservative and receives no VRAM credit. This estimates
offload suitability, not GPU compute speed or tokens per second. No model is loaded
or benchmarked for ranking; the existing runtime device query only reads device information.
These are deterministic heuristic points, not benchmark measurements. Paths break ties.
The installed collection is manually tested for tool calling before deployment; remove
models that fail that testing. Tool-test history is informational and never adds points
or excludes a model. A new computer needs no previous tests or runtime measurements.
A template or model name alone does not establish verified Hermes compatibility.

Optional `llm_fit` fields in a model profile are `tool_calling` (`unknown`,
`experimental`, `verified`, or `incompatible`) and `capability_evidence` to document
manual testing (both informational only), `kv_bytes_per_token` with `memory_evidence` for otherwise unsupported KV layouts,
and `extra_overhead_bytes`. Existing profiles/settings stay in place; canonical path
matching preserves their meaning after moving weights into drop-in and linking old paths.
Only known local server arguments (`--reasoning-budget N` currently) are accepted by
this startup flow so download/model/context flags cannot invalidate its analysis.
The existing GGUF CLI arguments remain available.

### Learning from actual performance

Normal auto/default/manual selections open the original application menu first. When chat starts,
then a passive sampler reads only numeric llama.cpp request timing lines after server
readiness. It issues **no extra requests or test prompts**. It records measured server
load time, prompt-processing/generation token counts and durations, and observed server
or session failures. Prompt text, responses and tool arguments/results are not copied
into performance diagnostics or the cache. Builds without recognized timing lines simply
provide no throughput observations; token speed is never inferred from wall-clock chat
or tool execution time. Sampling does not measure tool correctness or task completion.

Observations append to `logs/llm-fit-diagnostics.txt`. A bounded reusable cache lives at
`state/llm-fit-performance.json` (64 recent events per identity, up to 128 identities).
Matching requires CPU/architecture/core availability/flags, RAM ceiling, backend/GPU
identity, model and runtime file signatures, context, effective thread count, server
arguments and explicit chat-template signature. File signatures use size, modification
time and a 64 KiB header digest, not a full weight integrity hash. Moving the USB to
another mount does not itself change identity. Unknown hardware identity disables reuse.
Current available RAM is **always** checked afresh and cannot be overridden by history.

Automatic ranking uses hardware estimates only. Cached timings, load times and failures
never change selection scores. Passive observations remain available for diagnostics;
telemetry write failures do not interrupt chat. Direct CLI/queue pathways do not enable this sampler.

For an intentional comparison, choose original application menu option **11**, or run:

```bash
bash launch.sh --benchmark-installed
```

This tests only currently eligible GGUF models, rechecks RAM before each model, starts
one owned server at a time, verifies its identity, and sends three identical requests
for up to 64 tokens, with temperature 0, seed 42 and prompt caching disabled. Requests
have a maximum 120-second timeout each; server startup uses the existing configured
startup timeout. Timings come from the local server response; generated text is discarded.
No Hermes tools or real queued tasks run. Each model is attempted once; failures are logged
and cleaned up, and Ctrl+C stops the benchmark. Details stay in the diagnostic file,
including the observation source. This is a speed comparison, **not a tool-reliability or
agent-quality benchmark**. Models that do not currently fit are skipped. This command
requires the local llama.cpp runtime; it does not require Hermes to be installed and
never installs or downloads anything. A missing runtime returns a failure status.

### Persistent diagnostics and tests

Detailed reports append to **`logs/llm-fit-diagnostics.txt`** on the USB. The console
shows concise progress, errors and ordinary interactive chat. Reports contain timezone
and run ID, local hardware/device observations, GGUF scalar metadata, estimates,
classifications, scoring factors, selection and fallback reasons, readiness/model identity,
SDK prompt readiness, elapsed times and final outcomes. They exclude prompts and tool
results. Existing reports and unrelated session logs are preserved.

`fit_diagnostics.DiagnosticRun` provides `write(category, **values)` and `finish(outcome)`;
future benchmarks can append measured values under separate categories. Worker readiness
attaches to the parent run ID after actual SDK initialization, immediately before the
interactive prompt. Tests never run automatically at startup.

```bash
# Use hermes/python/bin/python3.12 instead of python3 when the bundle is present.
python3 -B run_fit_tests.py
python3 -B run_fit_tests.py --pattern test_llm_fit.py
# Normal independent unittest output is also available:
python3 -B -m unittest discover -s tests-hermes -p test_llm_fit.py
```

The diagnostic runner captures detailed test output into the same append-only text log,
prints a short result and preserves a failing exit code. Tests use synthetic fixtures and
local mock servers, not your real task queue or password audits. Existing ignore rules
already cover runtime logs/models and Python caches; narrowly scoped diagnostics/rotation
and `.llm-fit-artifacts/` / `llm-fit-test-output.*` rules are added. Measured-performance JSON/lock files are explicitly ignored as well. Test source remains
versionable. Ignore rules alone cannot untrack any previously tracked generated file.

## Terminal console, YOLO and quick testing

This launcher uses the **real Hermes SDK** with its own simple terminal console, rather
than Hermes's full-screen TUI. The `You>` and `Hermes>` prompts are intentional. It displays
`YOLO ON`: `HERMES_YOLO_MODE=1` auto-approves supported tool actions. YOLO is a launch
mode of the standard Hermes build, not a separate version. Tools run as the logged-in
Ubuntu user. This does not supply a sudo password, grant root, or remove Hermes's built-in
hard restrictions.

The moon animation is disabled in the USB console. Owned line-based CPU progress stops
when the request/session ends. The menu starts the supervisor in a separate process
session and forwards one Ctrl+C; cleanup ignores repeated interrupts while it closes
workers, the model, and flushes the USB. Ctrl+C returns to the menu; `/quit` exits chat.
Clearing the terminal does not stop a process—use Ctrl+C or `/quit`.

The regular 9B model remains selected. Its hidden reasoning budget is now zero to avoid
spending hundreds of CPU-generated tokens before an ordinary answer. Model-specific
settings in `model-profiles.json` choose context, output budget and tools, and GGUF
metadata caps the server context to the model's advertised native capacity. Chat has a
shorter output budget than autonomous task sessions. The local compatibility setting
does not modify the vendor SDK or advertise an invented context size.

For quick feedback, choose **main menu 6** and select one of:

| Model | Installed GGUF | Purpose |
| --- | --- | --- |
| SmolLM2 360M Instruct | Q8_0, 386 MB | Very small conversation/launch smoke tests |
| Qwen2.5 0.5B Instruct | Q4_K_M, 491 MB | Fast conversation and basic tool experiments |

Both are pinned to repository revisions and verified against their published SHA-256
values. These small models are test models, not dependable red-team agents or completion

`prompt.txt` is the standing context file, editable through menu 7. It now focuses on

## Plain-English tasks

Put your tasks in **`tasks.txt`**, separating them with a line containing `---`:

```text
Inspect calculator.py and fix addition. Add tests for positive, negative and zero inputs.
Run the tests and fix failures.
---
Write a short README explaining how to run calculator.py.
```

**No `VERIFY:` line is required.** Existing `VERIFY:` lines remain compatible as extra
checks, and old JSON queues still work. `tasks.example.txt` provides a new plain-English
example. Your original task prompts and optional checks were preserved during migration.

For unattended execution, starting the model and task loop together:

```bash
bash launch.sh --run --tasks tasks.txt
```

Or select menu option **3**. For direct interactive chat without the menus, use:

```bash
bash launch.sh --chat
```

The launcher installs no Ubuntu login hook.

`launch.sh` is the normal entry point. `setup.sh` repairs the pinned model/server and
reinstalls the cached Hermes dependencies. `setup_hermes.py --offline` repairs Hermes
without network access. You do not need to run setup on every launch. The supplied
runtime, source archives, wheel cache and hash-pinned dependency lock support moving
the drive to another compatible Ubuntu computer. Model downloads need internet access;
running installed models and local tasks does not.
The model downloader falls back to portable Python when the host has no curl and uses
the USB's certificate bundle for HTTPS lookups.

## How the task loop decides to stop

The loop follows the Ralph idea while keeping active work intact. A worker uses 32-turn
segments; reaching that turn budget automatically continues with the same conversation,
Hermes process registry and tracked commands. It no longer has a fixed 40-minute wall-clock
cutoff. Up to 16 segments are available before the outer loop needs a fresh worker, and
**the outer task loop has no attempt limit**. Errors, exhausted workers, missing evidence,
and negative reviews cause another attempt. Restarting the launcher resumes unfinished
tasks. Changes to a task invalidate its earlier completion; unchanged completed tasks are
skipped.

Long terminal jobs use the USB-local `capstone-job` supervisor. It starts one detached,
named command, records its PID, command, timestamps, output and exit status under
`state/jobs/`, refuses accidental duplicate starts, and remains alive across fresh AI
turns. Workers inspect or wait for that same job instead of restarting it. Tools such as
John also use their own named recovery session on the USB. The Hermes batch timeout is
disabled for these waits while the normal seven-day terminal ceiling remains available.
Ctrl+C still stops the model/task runner; a durable job can be inspected or deliberately
stopped with `capstone-job status NAME` or `capstone-job stop NAME`.

The AI receives the queue task ID through `CAPSTONE_QUEUE_TASK_ID` and uses it as the
durable job name. `capstone-job list`, `status`, `log` and `wait` are read-only inspection
operations. `start` refuses a duplicate or an already-recorded result; after inspecting a
failed job and its tool-specific recovery file, `start --restart NAME -- COMMAND` archives
the old status before launching the recovery command.

A fresh reviewer uses tools to inspect the actual files and run appropriate checks against
the original request. The worker saying “done” never completes a task. A reviewer must
return a positive structured verdict with evidence and no remaining work, and the runner
must have recorded successful independent observations. If a model returns prose, a
structured local model call formats the review's actual observations into a
verdict. Optional legacy checks run afterward. Each task's original request remains the
acceptance criterion; there is no agent-editable completion marker.
llama.cpp constrains that JSON during generation. The reviewer must still perform
a successful independent inspection before a positive verdict can complete a task.
Exact file-content requirements call for raw-byte checks, including newline counts.
For password audits and scans, a partial result, timeout, unsupported claim or abandoned
background process is insufficient; the reviewer is explicitly required to establish that
the requested targets or candidate set were actually processed. Full RockYou password
audits have an additional non-model validator: completion requires a zero-exit durable
John job whose provenance includes RockYou and `--format=crypt`, whose log shows hashes
were loaded, and whose log contains John's `Session completed` exhaustion marker. A
previously accepted audit lacking that evidence is reopened automatically.

This is AI review, not a mathematical proof. A model can miss requirements; task clarity
and the selected model affect results. An impossible task, unavailable privilege, failed
hardware, or missing input cannot be made complete by looping. Such tasks remain open
and retry rather than receiving a fabricated success. **Ctrl+C** interrupts the run and
saves progress. Power loss can interrupt an action after it has executed but before its
result is saved; fresh sessions are instructed to inspect before repeating actions.

Runtime records:

- `state/task-loop.json`: task status, attempts, progress, review evidence.
- `logs/sessions/`: original requests, real tool observations and final responses.
- `logs/server.log`: llama.cpp startup and inference output.
- `state/hermes/`: USB-local Hermes configuration and session data.
- `state/jobs/`: durable command status, history and output logs.
- `workspace/`: default folder for task files. Existing user files were retained.

To rerun an unchanged queue with a separate progress record:

```bash
bash launch.sh --run --tasks tasks.txt --state state/another-run.json
```

Hermes executes as the current Ubuntu user and has that user's terminal and filesystem
permissions. It cannot conjure a sudo password or bypass operating-system permissions.
The unattended configuration approves ordinary supported tool actions automatically;
Hermes's own hard restrictions still apply. Commands the agent deliberately detaches
outside its tracked tool processes, host services started through service managers, or
processes surviving forced power loss cannot be promised to close automatically.

## Models and CPU performance

The selected model is **Qwen3.5-9B Q4_K_M**, a 5.68 GB quantization by Unsloth of Qwen's
model. The old Qwen2.5-Coder-7B model is preserved. The new model has native support for
long context and tool use. The default Hermes/llama.cpp path now uses a compact system prompt and a
16,384-token context for CPU responsiveness. The local-only SDK compatibility setting
uses the actual server context rather than forcing a 64K floor. This compatibility
setting applies only to the local agent process. Select models that actually support their configured
context and tool calling.
Smaller or poorly instruction-following models may print commands instead of calling
tools, or fail review repeatedly. Changing harnesses cannot guarantee model competence.

The observed 9B CPU test used roughly 10.7 GB resident RAM and generated about 4 tokens
per second on this host. First prompt processing took about two minutes. Tasks involving
many tool calls can take minutes. Your Ubuntu CPU and USB speed will affect timings.
`config.json` controls the selected model, port, CPU threads, context, generation length,
session limits, command timeouts and retry delay. All inference uses zero GPU layers.

## Portable Ubuntu toolkit

`toolkit/` contains a compact, terminal-only assessment set built from Ubuntu packages:

- discovery and clients: Nmap/Ncat, Netcat, iproute2, ping, Curl, DNS, SMB/RPC,
  LDAP, NetBIOS and SNMP tools;
- password auditing: Hashcat 7.1.2 with bundled PoCL CPU OpenCL, John the Ripper,
  Hydra, Crunch and `pw-inspector`;
- content discovery: Gobuster and FFUF;
- local inspection: `getcap`, `getpcaps`, `capsh`, `lsof`, `file`, `strings`,
  `readelf`, `objdump`, `jq` and BusyBox.

The official Kali `wordlists` 2026.2.0 package supplies an uncompressed
`toolkit/share/wordlists/rockyou.txt` (139,921,507 bytes). Its original package is kept
in the checksum-pinned repair cache. Use these tools and password candidates only on
systems and accounts you are authorized to assess.

Hermes puts `toolkit/bin` on its PATH automatically, for both backends and task/chat
sessions. No host `apt install` is needed during a normal launch.

Each wrapper uses the USB's private dynamic loader and shared libraries, rather than
injecting toolkit libraries into Python or the model server. Nmap's probes, service
signatures, scripts and other data are included, along with a CA bundle and license files.
All symlinks are materialized as regular files for exFAT. The manifest records Ubuntu
package versions and SHA-256 values checked against signed Ubuntu indexes. A separate
manifest pins the official Kali data package by SHA-256. Cached `.deb` files allow
verified offline repair:

```bash
hermes/python/bin/python3.12 -s -B setup_toolkit.py --offline
```

Repair uses temporary space in the host's `/tmp` and its essential `dpkg-deb` command;
it installs no packages and runs no package-maintenance scripts. Normal toolkit execution
reads its executables, libraries and data from the USB. To use the same tools yourself:

```bash
source toolkit/env.sh
nmap --version
```

**Menu 10** shows tools, runs a self-test against a temporary **127.0.0.1-only** HTTP
service, or repairs the bundle. The self-test checks real Nmap open-port/service detection,
Netcat/Ncat connections, Curl responses, passive interface information, CPU OpenCL and a
synthetic two-candidate Hashcat recovery. It does not scan the connected LAN. Its receipt
is `logs/toolkit-self-test.json`. Hashcat's first CPU kernel build may take several
seconds; compiled kernels are cached under `state/tool-home/` on the USB.

John's Debian build expects a per-user `.john/john.conf`. On its first invocation the
wrapper creates that file in the logged-in user's home only when it is absent; existing
John configuration is preserved. John result/session files consequently use that user's
normal `.john` folder.

For the request “list machines and their services on this computer's network,” the agent
can inspect `ip -j address show` and `ip -j route show`, determine the requested connected
subnet, then use Nmap and save XML/text evidence under `workspace/`. TCP connect scanning
(`-sT`) and service detection (`-sV`) work as an ordinary user. Raw SYN/ARP/UDP operations
and packet capture may need root/capabilities supplied by Ubuntu; exFAT cannot carry Unix
file capabilities. YOLO cannot provide those privileges. Filtered/offline hosts and
non-default ports mean an inventory cannot promise every machine or every running service.

To grow this kit, add selected Ubuntu packages and their dependency closure to the signed,
hash-pinned cache, then rebuild the regular-file bundle and test its commands on clean
Ubuntu. The current set occupies about 1.9 GB including caches and RockYou. Tools with
hard-coded system paths, Python runtimes, kernel modules, or required capabilities need
individual packaging work. The installed binaries and private loader were tested in an
Ubuntu 26.04.1 x86_64 userland; other Ubuntu releases or CPUs have not been physically
tested. Tools still run with the logged-in user's permissions: this bundle does not grant
sudo, access to protected password hashes, packet-capture rights or raw-socket capabilities.

## Temporary File Management (SOURCE)

Launch this version from its own directory with `bash launch.sh`. Select a model
using the existing startup menu, then choose **12) Temporary File Management** in
the application menu. `bash launch.sh --chat` also creates managed scratch
storage, but enters chat directly without the main menu.

Each application supervisor creates a private mode-0700 `/tmp/hermes_session_*`
workspace using Python's secure `mkdtemp`. `TMPDIR`, `TMP`, `TEMP`, and Python's
cached temporary location point there. Model servers and Hermes SDK workers inherit
the scratch path. A launched application subprocess owns a separate workspace.
This covers temporary files made through the standard temporary APIs; it does not
move saved chat/task requests, results, logs, or user-created tool outputs.

The submenu displays the exact session ID/path, ownership validation, file and
directory counts, byte usage, and inspection errors. It never scans `/tmp`.
Active-session cleanup is conservatively deferred until shutdown, because tools
or inference may still need files. Confirm the shutdown-cleanup prompt, then exit
normally. Automatic cleanup also runs without that confirmation on normal exit,
unwinding errors, Ctrl+C exit, and handled SIGTERM/SIGHUP. Ctrl+C in menus retains
the existing return-to-menu behavior. Workers and model servers stop through the
existing shutdown handlers before the supervisor cleans its workspace. Cleanup
reports whether removal succeeded; missing directories are handled gracefully.

Minimal verification records live on the USB in `state/temporary-sessions/`.
Recovery reviews only those recorded paths, checking the host boot, current UID,
private directory permissions, device/inode, and matching random-token marker.
A directory lock protects active sessions without relying on PID identity. Owned
model/worker subprocesses inherit the lock, protecting their scratch storage if
the supervisor crashes. Recovery rechecks the lock and identity immediately before
confirmed deletion. Symlink substitutions are rejected; descriptor-based deletion
does not traverse symlinks inside the workspace. Invalid, inaccessible, active,
or unverifiable records are reported and preserved. Another host/boot's records
are deliberately preserved for manual investigation; moving the USB does not
establish ownership on the new host. SIGKILL and power loss cannot run shutdown
cleanup. Never delete directories merely because their names resemble HERMES.

**Restart requires no setup:** cleanup targets only the verified session directory.
`models/`, `runtime/`, `hermes/` (Python and installed packages), `toolkit/`,
configuration, USB caches, persistent sessions, logs, and workspace outputs remain
on the USB. `setup.sh` delegates preparation to `prepare.py`; setup installs these
persistent assets, not session scratch dependencies. Cleanup invokes neither setup
nor package/model downloads. It uses standard-library filesystem operations and
needs no sudo. If workspace creation fails (including read-only USB metadata),
startup stops with an error rather than enabling untracked cleanup.

Limitations: third-party engines, GPU drivers, and shell tools may ignore temporary
environment variables or explicitly write elsewhere. Existing USB runtime caches
remain persistent; legacy `state/tmp` contents are not automatically removed.
Detached processes outside the owned worker/server lifecycle are not guaranteed
to release resources. HERMES does not promise zero host artifacts. Failed cleanup
is reported without broadening its deletion scope.

Offline validation: `python3 -B -m unittest discover -s tests-hermes`.
For a real-model check on a prepared USB: run `bash launch.sh`, select the existing
default AI, inspect menu 12, return and start chat with option 1, ask a short
question, exit chat, request shutdown cleanup in menu 12, and exit both menus.
Confirm each reported workspace was removed. Run `bash launch.sh` again, select
the same model, and ask another question without running setup. To check crash
recovery, interrupt a disposable session with SIGKILL, ensure its owned workers
have exited, then review its record using menu 12 option 4 on the same host boot.
